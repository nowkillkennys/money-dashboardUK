## Architecture decision points after inspection

The base is already Next.js with a server-gated Supabase/PostgREST data path; the old implementation is Express/PostgreSQL with transaction-oriented services. Choose persistence before migrating real data, without reopening the adopted frontend decision.

1. **Preferred narrow path to evaluate:** retain Next route handlers and the current repository/query façade; put authoritative financial commands behind typed server services and a PostgreSQL repository. If retaining Supabase, implement transactional RPC/database functions for linked events, reconciliation and idempotency rather than client request chains. This minimises UI disruption while requiring new migrations, permissions and integration tests. Local test infrastructure must not depend on provisioning a cloud project.
2. **Alternative:** use a dedicated adapted Express service behind Next. This can reuse more transaction plumbing but adds a service, auth/session translation and deployment boundary. Select only if measured extraction complexity justifies that operational cost; do not run the existing legacy service against its database as a shortcut.
3. **Not sufficient:** add GBP and point existing screens at old APIs, or keep independent client writes for authoritative balances. That loses owner, reconciliation and atomicity guarantees. Do not silently treat the old numeric owner IDs as the new fixed UUID.

The security review additionally identifies a critical PIN database-error/setup-claim boundary requiring repair before private persisted use: a database failure must fail closed rather than imply that setup is available, and initial owner/PIN setup must be claimed atomically with a tested recovery path. Include concurrent setup, unavailable database and invalid/expired session cases in phase 1. The current fixed owner is a single-household boundary, not a future tenant model. Future multi-user use requires server-derived authenticated owner identity throughout commands, repositories, uniqueness constraints and cross-entity references; neither a client-supplied UUID nor replacing a constant alone establishes isolation.

Keep separate domain types for account identity, reported snapshot, posted/pending ledger events, payment inclusion decisions, typed statement observations, purchase plans and forecast scenarios. UI adapters may supply existing cards/tables with display numbers; the authoritative boundary remains exact money. A provider observation becomes a reviewed snapshot/event through the same command path as manual/PDF input, never a parallel overwrite path.

## Future migration/export contract and rollback

No real-data export is part of this work. A later explicitly authorized migration should use a read-only exporter from a consistent source snapshot, never connect the new UI directly to a live old schema. Its versioned manifest should include source commit/schema, export ID/time, currency/timezone conventions, entity counts and integrity hashes. Export only approved financial fields: account IDs remapped through an explicit owner-scoped mapping, snapshots and provenance, payments/status, reconciliation dispositions, correction history, reviewed statement observations and necessary audit/idempotency lineage. Exclude credentials, session tokens, environments, raw statement files/text, PAN, names and unrelated personal data.

The destination importer first validates/dry-runs a staged copy. Preserve decimal strings, dates, source identity, versions and unresolved states; never infer inclusion merely from event dates. Use migration-specific source/entity keys, owner mapping and batch ledger so replay has one effect; validate foreign references, enum/rate basis and ownership before a transaction commits. Source debt IDs must not collide with upstream UUIDs. A financial event mirrored into a retained transaction view needs a stable link so it cannot be counted twice.

Reconcile per-account reported/tracked/unresolved state, event counts, sums by status/currency/date and dashboard totals before cutover; discrepancies block adoption. Test malformed/truncated exports, duplicate runs, interrupted batches, concurrent source changes, unknown fields and rollback with synthetic exports first. Encrypt any authorized real-data artifact, limit access/retention and log counts/IDs rather than values. Rights/export workflows for future users remain a product feature, not a side effect of this internal migration format.

Rollback before cutover is deletion of the isolated destination batch/store and disabling its feature flags; the legacy applications continue untouched. After a later real cutover, use a verified destination backup and a documented read-only cutover boundary rather than silently writing diverging histories into both apps. Schema reversions must not discard accepted financial records. For the current bounded demo, revert the new branch's commits and discard only its synthetic data. No legacy database, `.env`, private files, running process or port is modified by this plan; no public deployment or external connection is requested.
