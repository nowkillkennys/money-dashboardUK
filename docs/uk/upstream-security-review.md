## Decision

Retain the selected base for a UK personal-first application. Its single-owner model is explicit and can support a private deployment after bounded repairs. It is **not a multiuser authentication or tenant-isolation foundation as currently implemented**. Publishing source or a synthetic demo and offering accounts to the public have different release gates. Do not expose real financial data or enable public signup before the gates below are satisfied.

## Database and secret boundaries

The server checks HTTPS for its configured Supabase URL (`lib/supabase-server.ts:39-46`); user input does not choose the data-gateway destination. Yahoo quote destinations are fixed and symbols are encoded/validated (`app/api/stocks/route.ts:7-24`, `lib/money/yahoo-finance.ts:110`). No general arbitrary-URL proxy was identified there. The push path above is the notable SSRF candidate.

Migration 007 revokes direct anonymous table access; 008 grants it back subject to a gateway-secret RLS predicate; 009 changes the authorization helper to SECURITY INVOKER and pins function search paths. These must be considered together, not described as simply "anonymous access disabled" (`supabase/migrations/008_gateway_secret_access.sql:99-145`, `009_gateway_function_hardening.sql:5-48`). The SQL contains a fixed gateway-secret hash and 008 overwrites that configuration on replay (`008:18-26`). Generate a deployment-specific secret/hash using a reviewed provisioning mechanism; do not assume the checked-in hash matches any local secret or is itself the raw credential. Verify fresh schema and migration upgrade paths separately in disposable Postgres, including anonymous/authenticated/service-role denial tests. No SQL was executed in this review.

Cookie flags are HttpOnly, production Secure, SameSite=Lax and path=/ (`verify-pin:58-64`). Bcrypt cost 10 and legacy SHA256 upgrade exist (`lib/supabase-server.ts:79-112`). These are useful controls, but do not fix initial-claim, revocation or identity issues. Error logging includes database error messages and complete AI exceptions (`app/api/ai/chat/route.ts:244`, `voice:236`); upstream error content could expose request details. Redact and classify errors before any real-data deployment. Do not commit credentials, logs or telemetry containing financial data; this review intentionally did not read private env files and is not a history-wide secret scan.

`next.config.mjs` sets useful framing, MIME and referrer headers, but its CSP permits unsafe-inline and unsafe-eval scripts and broad HTTPS images. Remove development allowances in production after compatibility verification and apply an explicit external connection policy. Browser CSP does not restrict server-side external requests.

## Scoped initial UK slice verdict

The latest scoped source review supports **a local, synthetic-only preview**, with the executed browser/server-policy evidence recorded in verification.md. It does not approve real records, cloud connections, a public server or completed UK migration. No new blocker to that tightly bounded preview was found in the reviewed initial changes.

`compose.uk.yml` exposes a fixed non-root Nginx ingress only at `127.0.0.1:13021`; the application itself has only an internal Docker network, non-root image user, read-only filesystem with temporary cache, no preview host mounts, dropped capabilities, no-new-privileges and resource limits. `.dockerignore` excludes `.env`/`.env.*` except the example, `.git`, audit work and generated artifacts. The dependency installation stage uses registry access and disabled lifecycle scripts; the production build alone runs network-disabled. Do not describe the complete build pipeline as having zero network access. The image currently copies the complete installed node_modules graph, including test/dev packages; that is acceptable for this disposable preview boundary but needs a separate minimal production packaging review. Parent reports an external-host fetch failed from the runtime; browser-origin egress is a separate boundary to verify.

The data changes are internally coherent for the reviewed examples: GBP checking accounts and card liabilities; monthly synthetic salary; foreign investment cash denominated in USD; the GBP-to-USD transfer includes an explicit destination amount; its USD cash holding matches the investment-account balance. `lib/money/uk-locale.ts` defines fixed illustrative currency units per USD, and `convertCurrency` uses amount/source-rate*destination-rate. The demo hook and server helpers choose those rates without providers; an empty quote result is not represented as a live valuation. Tests now target reciprocal GBP/USD and GBP/EUR conversion, transfer conservation and card repayments reducing cash and liabilities once. These are meaningful bounded invariants, not proof of all financial calculations or statement import correctness.

The fixture date generator now uses a London civil date, and its helper rejects invalid civil dates and supports DST-boundary day offsets. Some inherited display/reminder code still uses browser-local Date operations and `toLocaleDateString('en-GB')` without an explicit London time zone; this slice should not be called a complete UK calendar/time-zone audit. The non-demo FX fallback still substitutes one for unavailable rates; it remains outside the synthetic preview contract and must not be used to value real records silently. Existing import, credit/debt domain, precision, tax and UK institution requirements remain migration work.

Before calling this preview verified, retain evidence of the actual loopback build/runtime, no browser external requests on exercised routes, API/image/service-worker denial, empty synthetic stock response, both-flag startup refusal, desktop/mobile rendering and no browser runtime errors. The newly added `e2e/uk-smoke.spec.ts` covers representative routes and blocks/logs attempted external requests; passing it establishes those exercised paths only. The saved dependency advisories and upstream production blockers remain open even if all preview checks pass.
